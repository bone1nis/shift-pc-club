# Мониторинг

## Grafana простыми словами

Мониторинг отвечает на два вопроса: «всё ли работает прямо сейчас» и «что произошло, когда сломалось». Он состоит из четырёх программ:

| Программа      | Зачем                                                                                                                      |
| -------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **Prometheus** | Каждые 15 секунд опрашивает сервисы и хранит числа: сколько запросов, сколько ошибок, жив ли воркер, сколько событий ждёт. |
| **Loki**       | Хранит журналы (логи): текстовые записи о том, что делали сервисы и какие были ошибки.                                     |
| **Alloy**      | Курьер: забирает файлы журналов Laravel и proxy и передаёт их в Loki.                                                      |
| **Grafana**    | Окно, через которое всё это видно: графики, журналы и оповещения. Сам ничего не собирает.                                  |

Мониторинг нужен разработчику и дежурному; на работу клуба и сайта он не влияет (его можно не запускать, брони при этом работают).

### Как войти

1. `docker compose --profile monitoring up -d` (или `./scripts/start.sh --monitoring`).
2. Откройте `http://localhost:3038/`: логин `admin`, пароль — `GRAFANA_PASSWORD` из файла `.env` (`grep GRAFANA_PASSWORD .env`).

### Что где лежит в Grafana (меню слева)

- **Dashboards → SHIFT** — готовые панели. «SHIFT · Operations»: запросы в секунду, доля ошибок 5xx, время ответа p95, очередь событий (outbox), сердцебиение воркера и планировщика. «SHIFT · Club business»: брони, отмены, сессии, начисления, оплаты, воронка сайта (данные из базы).
- **Alerting → Alert rules** — правила оповещений и их состояние.
- **Drilldown** — готовые «мастера» для метрик и журналов. Разделы Traces и Profiles отключены: трейсов (Tempo) и профилей (Pyroscope) в проекте нет, а пустые разделы показывали красную ошибку.
- **Explore** — ручные запросы: выбираете источник (Prometheus для чисел, Loki для журналов) и смотрите данные за нужный период.

### Что значат оповещения

Состояния: **Normal** — всё в порядке; **Pending** — условие выполняется, но ещё не дольше положенного времени; **Firing** — проблема держится, нужно разбираться.

| Оповещение                             | Что значит                                                          | Что делать                                                                                                 |
| -------------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| SHIFT API scrape target down           | Prometheus не может опросить Identity, Club или Booking.            | `docker compose ps`, `docker compose logs <сервис>`: контейнер упал или завис.                             |
| SHIFT API 5xx ratio elevated           | Больше 5 % запросов API заканчиваются серверной ошибкой.            | Explore → Loki: `{service="booking"} \| level="error"`; смотрите причину и `request_id`.                   |
| SHIFT API p95 latency above one second | 5 % самых медленных запросов дольше секунды.                        | Проверьте нагрузку на базу и RabbitMQ, ищите медленные запросы в журналах.                                 |
| SHIFT outbox delivery delayed          | Событие ждёт отправки в RabbitMQ дольше двух минут.                 | Проверьте `rabbitmq` и `booking-scheduler`; причина сбоя — в журнале Booking («Outbox publishing failed»). |
| SHIFT booking worker heartbeat stale   | Воркер Booking давно не отмечался.                                  | `docker compose logs booking-worker`, при необходимости `docker compose restart booking-worker`.           |
| SHIFT scheduler heartbeat stale        | Один из планировщиков (Identity, Club, Booking) давно не отмечался. | `docker compose logs booking-scheduler club-scheduler identity-scheduler`.                                 |

Если оповещение горит, а сервисы живы, сначала проверьте, не «залипшее» ли оно: в Alerting → Alert rules откройте правило и посмотрите, что показывает запрос. Раньше три правила горели постоянно из-за настройки «нет данных = тревога» (при здоровой системе условие возвращает пустой результат); сейчас для них «нет данных» считается нормой, а пропажу метрики ловит `absent()` внутри условия.

### Как читать журналы (логи)

1. Explore → источник **Loki**, период (справа вверху) «Last 1 hour».
2. Выберите метку `service` (identity, club, booking, proxy) или напишите запрос.
3. Полезные запросы:

Сервисы пишут в журнал не только ошибки, но и обычные события на русском языке: «Бронь №12 создана», «Сессия №5 продлена на 30 мин», «Вход выполнен: пользователь №3», «Письмо отправлено: уведомление №8», «Событие обработано: booking.confirmed». В записи только номера, без email, имён и паролей. Если в Explore видны только warning и error, снимите фильтр уровня (в Logs Drilldown выберите «All levels» или «info»).

```text
{service="booking"}                                  — всё от Booking
{service="booking"} | level="error"                  — только ошибки
{service="booking"} |= "Бронь"                      — всё про брони
{service=~"identity|booking"} | json | event="auth.login" — входы пользователей
{service=~".+"} | json | request_id="<номер>"      — весь путь одного запроса
{service="booking"} |= "Outbox publishing failed"    — строки с текстом
{service="proxy"} | status="502"                     — ответы 502 на входе
{service="booking"} | json | event_id="…"            — путь конкретного события
```

4. Каждая запись — JSON: `message`, `level_name`, `context` (класс исключения, `event_id`, `attempt`), `datetime`. Строку можно раскрыть. У записей proxy есть `request_id`: по нему находят один запрос от входа до сервиса.
5. Сверяйте время ошибки с графиком на дашборде: наведите курсор на всплеск и сузьте период вокруг него.

В журналы не попадают пароли, токены, cookies и заголовки Authorization; не вставляйте их в запросы и отчёты.

Дальше — подробности настройки.

Локальный мониторинг запускается профилем Docker Compose:

```sh
docker compose --profile monitoring up -d
```

Grafana доступна на `http://localhost:3038/`. Пользователь — `admin`; пароль берётся из `GRAFANA_PASSWORD` в приватном корневом `.env`. Не публикуйте этот файл и не вставляйте пароль в отчёты. Prometheus, Loki и Alloy доступны внутри Docker-сети, без отдельных публичных портов.

## Метрики и журналы

Prometheus опрашивает Identity, Club и Booking каждые 15 секунд через внутренний `/metrics`, а RabbitMQ — через порт 15692. Через публичный proxy `/metrics` закрыт. Метрика `up` показывает доступность scrape target, а не успешность пользовательского сценария.

Alloy читает журналы Laravel и proxy из подключённых volumes и передаёт их в Loki. В Grafana Explore выберите Loki, ограничьте период и сервис. Для ошибки пользовательского запроса используйте `request_id`, когда он присутствует в записи. HTTP 5xx требует проверки исключения в журнале; сам статус не объясняет причину.

Конфигурации находятся в `infra/monitoring/`: `prometheus.yml`, `loki.yml`, `alloy.alloy`, dashboards и provisioning Grafana. PostgreSQL datasource использует отдельную reporting-роль, а не пароль backend-сервиса. Бизнес-показатели не следует трактовать как подтверждение оплаты: начисленная стоимость и фактическая оплата — разные величины.

## Проверка состояния

```sh
docker compose --profile monitoring ps
docker compose logs --tail 100 prometheus loki alloy
docker compose logs --tail 100 identity club booking booking-worker
```

В Grafana проверьте datasource, диапазон времени и наличие данных. Пустая панель не означает отсутствие ошибок: причиной может быть недоступный target или неверный запрос. Настроенные правила оповещений включают недоступность API, рост доли HTTP 5xx, задержку запросов и состояние outbox; пороги и периоды ожидания задаются в `grafana/provisioning/alerting/shift.yml`.

## Безопасная диагностика

Не создавайте ошибки в demo-базе удалением таблиц и не публикуйте токены, cookies или пароли в журналах. Проверки отказов выполняйте на отдельных тестовых БД с выделенными ролями. Не удаляйте Docker volumes для восстановления мониторинга: они содержат историю и локальные данные. Перезапуск компонента не доказывает доставку событий — состояние outbox и обработку очереди проверяйте отдельно.

Наличие конфигурации не подтверждает доставку каждого оповещения или восстановление после простоя. Реально проверенные сценарии (например, `scripts/chaos-worker-kill.sh`) описаны в разделе про события; актуальные ограничения собраны в [статусе реализации](/status).

## Статистика сайта

Просмотры страниц и начало бронирования приходят анонимными событиями в таблицу `site_events` (Booking), успешные брони берутся из `bookings`. Grafana читает их через read-only представление `reporting_site_funnel_daily` (панель «Site funnel» на дашборде «SHIFT · Club business»). Просмотры не равны уникальным посетителям: идентификатор живёт только в `sessionStorage` вкладки, без cookie; «люди» считаются по хешу IP и User-Agent с суточной солью (сами значения не хранятся, связать визиты разных дней нельзя): отчёт показывает сумму уникальных за каждый день периода. События ботов и из чужих Origin не записываются; поле `environment` позволяет отделять демо и тестовые данные.
