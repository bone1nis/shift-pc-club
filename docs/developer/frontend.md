# Фронтенд: устройство, связка пакетов и поток данных

Эта страница объясняет, из чего состоит фронтенд, как пакеты монорепозитория связаны между собой и как данные добираются от backend до экрана.

## Общая картина

```text
                      браузер
                         │  один адрес: http://localhost:8088
                         ▼
                 nginx (прокси)
   ┌───────────┬──────────┼───────────────┬────────────────┐
   ▼           ▼          ▼               ▼                ▼
 сайт       админка     документация   /api/auth/*     /api/club/*  /api/booking/*
 Nuxt       Vue SPA     VitePress      Identity        Club         Booking
 :3000      :5173       :5175          (Laravel, Docker)
   │           │
   └─────┬─────┘
         ▼
 packages/ui        — общие компоненты и токены оформления
 packages/contracts — типы и схемы данных API
```

| Часть                 | Что это                                                           | Где                  |
| --------------------- | ----------------------------------------------------------------- | -------------------- |
| Сайт и кабинет игрока | Nuxt 4 с серверным рендерингом (SSR)                              | `apps/web`           |
| Админка               | Vue 3 + Vite, одностраничное приложение (SPA) по адресу `/admin/` | `apps/admin`         |
| UI-кит                | собственные компоненты, иконки, токены, Storybook                 | `packages/ui`        |
| Контракты             | TypeScript-типы, схемы Zod, JSON-схемы событий, типы из OpenAPI   | `packages/contracts` |
| Документация          | VitePress, адрес `/docs/`                                         | `docs`               |

## Как устроена связка пакетов (pnpm workspace)

Репозиторий — монорепозиторий на pnpm. Файл `pnpm-workspace.yaml` перечисляет папки-пакеты (`apps/*`, `packages/*`, `docs`), а корневой `package.json` собирает общие команды.

**Подключение без публикации.** В `apps/web/package.json` и `apps/admin/package.json` написано `"@shift/ui": "workspace:*"` и `"@shift/contracts": "workspace:*"`. После `pnpm install` pnpm не скачивает эти пакеты, а кладёт в `node_modules/@shift/` символические ссылки на соседние папки:

```text
apps/web/node_modules/@shift/ui        →  ../../../../packages/ui
apps/web/node_modules/@shift/contracts →  ../../../../packages/contracts
```

Поэтому `import { UiButton } from '@shift/ui'` в любом приложении читает файлы прямо из `packages/ui`.

**Без отдельной сборки.** У `@shift/ui` и `@shift/contracts` в `package.json` указано `exports: ./src/index.ts`, то есть они отдают исходный код (`.vue`, `.ts`), а не собранные файлы. Приложение собирает чужие исходники вместе со своими: правка кнопки в `packages/ui` сразу видна и на сайте, и в админке (горячая перезагрузка работает через границы пакетов). Минус один: потребителю нужен тот же стек (Vue, Vite), но у нас он везде общий.

**Алиасы.** Внутри приложения слои FSD импортируются через алиас `@fsd/*` → `src/*` (в Nuxt он задан в `nuxt.config.ts`, в админке — в `vite.config.ts` и `tsconfig.json`; для тестов — в `vitest.config.ts`). Пример: `import { useUserStore } from '@fsd/entities/user'`.

**Единые стили.** Оба приложения подключают `@shift/ui/tokens.css` (в Nuxt — `css: ['@shift/ui/tokens.css']`, в админке — импорт в `main.ts`). Это единственный глобальный CSS: шрифты, переменные, сброс.

**Общие настройки.** `tsconfig.base.json` (строгий TypeScript), `eslint.config.mjs` (правила и граница слоёв FSD), `.prettierrc.json`, `vitest.config.ts` и `playwright.config.ts` лежат в корне и действуют на все пакеты.

**Кто что запускает.**

| Команда                                                     | Что делает                                                  |
| ----------------------------------------------------------- | ----------------------------------------------------------- |
| `pnpm install`                                              | ставит зависимости всех пакетов и создаёт ссылки между ними |
| `pnpm dev:web` / `dev:admin` / `dev:docs` / `dev:storybook` | запускает один пакет (`--filter`)                           |
| `pnpm lint`, `pnpm typecheck`, `pnpm test:unit`             | проверки сразу для всех пакетов                             |
| `pnpm build`                                                | собирает сайт, админку, Storybook и документацию            |

## Сайт (`apps/web`, Nuxt)

Каталоги:

- `app/` — то, что требует Nuxt: `app.vue` (корень), `layouts/default.vue` (шапка + контент + подвал), `pages/*.vue` (маршруты), `plugins/` (TanStack Query, аналитика), `error.vue` (страница ошибки). Страницы здесь **тонкие**: `app/pages/account.vue` только подключает `AccountPage` из слоя `src/pages` и задаёт `noindex`.
- `src/` — весь остальной код по слоям FSD (`pages`, `widgets`, `features`, `entities`, `shared`).

Автоимпорт Nuxt отключён (`imports.autoImport: false`, `components: false`): всё импортируется явно, поэтому видно, откуда берётся каждый символ, и FSD-правила могут это проверять. Функции Nuxt (`useRoute`, `navigateTo`, `useHead`) берутся из `#imports`.

**Серверный и клиентский рендер.** Лендинг рисуется на сервере: данные каталога и профиля клуба берутся через `useAsyncData` + `$fetch`. На сервере запрос идёт во внутренний адрес API (`runtimeConfig.apiInternalOrigin`, по умолчанию `http://localhost:8088`), в браузере — по относительному адресу. HTML приходит уже с контентом, поэтому страница быстро показывается и хорошо индексируется. Личные данные (кабинет, бронирование) загружаются только в браузере: у сервера нет cookie пользователя.

**Состояние и данные.**

- Текущий пользователь — Pinia-хранилище `useUserStore` (`entities/user`): `load()` спрашивает `/api/auth/me`, `signIn`, `register`, `logout`.
- Данные кабинета (брони, сессии, устройства, уведомления) — TanStack Query (`useAccount`): кэш, обновление раз в 30 секунд, повторный запрос при возврате на вкладку. Текст уведомлений собирает `entities/notification` (`notificationText`).
- Выбор мест при бронировании — composable `useBookingSelection` с защитой от устаревших ответов и двойной отправки.

**Прочее.** Анимации появления блоков — директива `v-reveal`; PWA — модуль `@vite-pwa/nuxt`; SEO — теги и JSON-LD в `useHead`. Подробности — в разделе [Библиотеки фронтенда](/developer/libraries).

## Админка (`apps/admin`, Vue SPA)

Точка входа — `src/app/main.ts`: создаёт приложение, подключает Pinia и роутер, импортирует токены. Роутер (`src/app/router.ts`) работает по адресу `/admin/` (`createWebHistory('/admin/')`).

**Защита маршрутов.** Перед каждым переходом срабатывает `router.beforeEach`: если пользователь ещё не загружен, спрашивается `/api/auth/me`; если роль не `admin`, происходит редирект на `/login`. Страницы админки сами не проверяют права, а сервер всё равно проверяет их на каждом запросе: клиентская защита нужна для удобства.

**Общее состояние смены.** Хранилище `useOperationsStore` держит каталог, брони и сессии. Оно же даёт единую обёртку `run(action, success)` для всех действий администратора: защита от повторного запуска (`pending`), сообщение об успехе (автоскрытие через 6 с) и об ошибке, последующее обновление данных. Каждые 30 секунд оболочка (`AdminShell`) вызывает `refresh()`, а страницы реагируют на счётчик `tick` и перечитывают свои данные.

**Оболочка.** `widgets/admin-shell`: боковое меню на десктопе, на телефоне — верхняя панель с бургером и выдвижная панель. Страницы переключаются с анимацией, всплывающие сообщения «плавают» над страницей и не сдвигают контент.

## Как фронтенд общается с backend

**Один адрес.** Браузер ходит только на `http://localhost:8088`. Запросы к API идут по относительным адресам (`/api/auth/...`, `/api/club/...`, `/api/booking/...`), а nginx раскладывает их по сервисам. Благодаря этому у сайта, админки и API один origin: не нужны CORS-настройки, а cookie работают без исключений. В dev-режиме dev-серверы (`nuxt dev`, `vite`) дополнительно проксируют `/api` на тот же адрес.

**Клиент API.** Все запросы выполняет функция `api()` из `shared/api` (в сайте и админке реализации одинаковые):

1. Добавляет заголовки (`Accept`, `Content-Type`), cookie отправляются автоматически (`credentials: include`).
2. Для изменяющих запросов (не `GET`) подставляет `X-CSRF-TOKEN`. Токен берётся из cookie `XSRF-TOKEN`; если её нет, запрашивается `/api/auth/csrf` (под блокировкой Web Locks, чтобы две вкладки не делали это одновременно).
3. Ответ `419` (токен устарел) — один раз получает новый токен и повторяет запрос.
4. Ответ `401` (истёк токен доступа) — один раз вызывает `/api/auth/refresh` и повторяет запрос; если не вышло, отправляет на вход и запоминает страницу для возврата.
5. Ошибка `4xx/5xx` превращается в `ApiFailure` с кодом, сообщением и ошибками по полям (`fields`).
6. Успех: возвращается поле `data` ответа.

Для проверки формы ответа есть `apiParsed(схема, путь)`: ответ сверяется со схемой Zod из `@shift/contracts`.

**Аутентификация.** Токены лежат в HttpOnly-cookie (`shift_access`, `shift_refresh`), JavaScript их не видит; доступна только cookie `XSRF-TOKEN`. После входа фронтенд хранит лишь данные пользователя (имя, роль) в Pinia ([ADR 0001](/adr/0001-jwt-http-only-cookies)).

**Схема одного запроса (отмена брони).**

```text
кнопка «Отменить» (features/cancel-booking)
  → api('/api/booking/bookings/12/cancel', POST)
      → подставлен X-CSRF-TOKEN; cookie уходят вместе с запросом
      → nginx: /api/booking/* → Booking
      → Booking проверяет подпись токена, CSRF и Origin, права, правило отмены
      ← 200 {data: {...}}
  → сообщение «Бронь отменена», account.load() → обновление списка
```

**Типы и контракты.** Тип ответа берётся из `@shift/contracts`; часть типов генерируется из OpenAPI сервисов (`pnpm contracts:generate`), а `pnpm contracts:check` в CI проверяет, что они не отстали от backend. Схемы событий (`packages/contracts/events`) нужны backend-сервисам; фронтенд их не использует.

**Время.** Backend хранит время в UTC, клуб живёт по московскому времени. Перевод «настенного» времени клуба в UTC и обратно делает `shared/format` (`clubDateTimeToIso`, `clubDateTimeInput`) через `date-fns`, поэтому результат не зависит от часового пояса браузера.

**Опрос вместо WebSocket.** Свежесть данных обеспечивают периодические запросы (кабинет и смена обновляются раз в 30 секунд, [ADR 0005](/adr/0005-polling-before-websockets)).

## Как добавить новое

**Новый экран админки.**

1. Создайте слайс `src/pages/<имя>/` с `ui/<Имя>Page.vue`, `model/use<Имя>.ts` и `index.ts`, который экспортирует страницу.
2. Добавьте маршрут в `src/app/router.ts` (с `meta.title`) и пункт меню в `AdminShell.vue`.
3. Данные берите через `api()` и общее хранилище (`useOperationsStore`) для действий; типы — из `@shift/contracts`.

**Новое действие пользователя (кнопка с запросом).** Создайте слайс в `features/<действие>/` (логика в `model/`, разметка в `ui/`), подключите его на странице через публичный `index.ts`. Страница не должна знать, как внутри устроен запрос.

**Новый общий компонент.** Добавьте `Имя.vue` в `packages/ui/src`, экспортируйте в `index.ts`, напишите историю Storybook (`Имя.stories.ts`) и, если у компонента есть поведение, unit-тест в `tests/unit/ui-kit.test.ts`. Цвета и размеры берите из токенов.

**Новый запрос к API.** Если ответ используется в нескольких местах, добавьте схему Zod в `packages/contracts/src/schemas.ts` и вызывайте `apiParsed`. После изменения контракта backend обновите OpenAPI-типы командой `pnpm contracts:generate`.

## Организация кода

Оба приложения (`apps/web` — Nuxt, `apps/admin` — Vue + Vite) построены по Feature-Sliced Design: слои `app → pages → widgets → features → entities → shared`, зависимости направлены только вниз, обращение к слайсу — через его `index.ts` (проверяет ESLint, правило `fsd/boundaries`).

| Слой       | Что лежит                                                                                                     |
| ---------- | ------------------------------------------------------------------------------------------------------------- |
| `app`      | запуск, роутер, корневые компоненты (в Nuxt — тонкие `app/pages/*.vue`, которые подключают страницы из `src`) |
| `pages`    | экраны; данные экрана — в `model/use*.ts`, разметка — в `ui/*.vue`                                            |
| `widgets`  | крупные блоки: шапка и подвал сайта, секции лендинга, оболочка админки                                        |
| `features` | действия пользователя: вход, бронирование, отмена, правка профиля, правка оборудования, тарифов и зон         |
| `entities` | сущности и их представление: бронь, игровая сессия, пользователь, общее состояние смены                       |
| `shared`   | транспорт (`api`), форматирование, контейнер и общие мелкие компоненты                                        |

Логика (состояние, запросы) живёт в `model/` как composable или Pinia store, компоненты в `ui/` — это разметка и стили.

## Правила стилей

- Каждый компонент — `<script setup lang="ts">` + `<template>` + `<style scoped>`. Стили лежат рядом с разметкой.
- Глобально остаётся только `packages/ui/src/tokens.css`: шрифты, CSS-переменные (цвета, радиусы, шрифты, слои), сброс, типографика и `.sr-only`. Своих «общих» CSS-классов не заводим — нужен повторяемый кусок, делаем компонент.
- Цвета и размеры берём из переменных (`var(--acid)`, `var(--line)`, `var(--radius)`), числа вроде `#111212` повторять не нужно.
- Стили дочернего компонента из родителя меняем только через `:deep()` и только для корневого элемента (например, отступ у кнопки).

## UI-кит `packages/ui`

Нативные виджеты браузера (`datetime-local`, `date`, `select`, `checkbox`, `number`, `confirm`/`prompt`) не используются: у всех есть собственные доступные компоненты.

| Компонент                                                                                    | Назначение                                                                               |
| -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `UiButton`                                                                                   | кнопка и кнопка-ссылка (`as`), варианты, размеры, `loading`                              |
| `UiField`                                                                                    | текстовое поле с подписью, ошибкой и подсказкой (`hideLabel` скрывает подпись визуально) |
| `UiNumberInput`                                                                              | число с кнопками −/+, стрелками и ограничениями `min`/`max`/`step`                       |
| `UiSelect`                                                                                   | выпадающий список (listbox, клавиатура, поповер)                                         |
| `UiCheckbox`, `UiSwitch`                                                                     | флажок и переключатель                                                                   |
| `UiSegmented`, `UiTabs`                                                                      | выбор из нескольких вариантов; вкладки с ролью `tablist`                                 |
| `UiCalendar`, `UiDatePicker`, `UiDateTimePicker`                                             | календарь, поле даты, поле даты и времени (шаг в минутах, ограничение `min`)             |
| `UiDialog`                                                                                   | модальное окно: фокус, `Esc`, ловушка `Tab`                                              |
| `UiPanel`, `UiStatCard`, `UiTable`, `UiNotice`, `UiEmpty`, `UiStatus`, `UiSeatMap`, `UiLogo` | контейнеры, таблица, сообщения, статусы, схема зала                                      |

Значение полей даты и времени — «настенное» время строкой (`YYYY-MM-DD`, `YYYY-MM-DDTHH:mm`) без часового пояса; перевод в UTC выполняют приложения по времени клуба.

Каждый компонент описан в Storybook (в разработке — `http://localhost:6006/`, его запускает `./scripts/dev.sh`; в продакшен-стеке Docker — `/storybook/`) и покрыт unit-тестами (`tests/unit/ui-kit.test.ts`). Новый компонент добавляйте вместе с историей и тестом.

Подключённые библиотеки (vue-query, PWA, VueUse, auto-animate) и причины, по которым не взяты другие, описаны в разделе [«Библиотеки фронтенда»](/developer/libraries).
