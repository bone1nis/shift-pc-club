# Архитектура и безопасность

```text
Browser → nginx proxy → Nuxt site / Vue admin
                   ├→ Identity API → shift_identity
                   ├→ Club API → shift_club
                   ├→ Booking API → shift_booking
                   ├→ Realtime API → shift_realtime
                   └→ Reverb (WebSocket /app) ← realtime-worker
                         ↕ RabbitMQ events
             Redis cache/locks · PostgreSQL · Mailpit (local)
```

Nginx даёт единый origin: сайт `/`, админка `/admin/`, API `/api/auth/`, `/api/club/`, `/api/booking/`, `/api/realtime/`, WebSocket `/app`, документация `/docs/`, Storybook `/storybook/`. Внутренние маршруты API закрыты на proxy и требуют внутренний токен при межсервисном вызове.

Identity выдаёт краткоживущий JWT access token и отдельный вращаемый refresh cookie с HttpOnly; изменяющие запросы проходят CSRF-проверку. Приложения не сохраняют JWT в Pinia/localStorage. Проверка защищённого запроса сверяет актуальную auth-сессию в Identity; если Identity недоступен, запрос должен завершиться отказом. Администраторская роль всегда проверяется на сервере.

Каждый сервис изменяет только свою базу. Booking владеет бронями, резервированиями мест и игровыми сессиями; Club владеет каталогом; Identity владеет аккаунтами и входами; Realtime владеет чатом брони и ключами устройств; жалобы хранит Club. Событие записывается в outbox внутри той же транзакции, что и бизнес-изменение. RabbitMQ publisher confirms и повторная доставка не делают обработку exactly-once: consumer-ы обязаны быть идемпотентными.

Публичный каталог не требует входа. Закрытые API вызовы используют cookie credentials, CSRF заголовок и проверку роли. Не логируйте пароли, Authorization, cookies, токены и тела форм. Не добавляйте в метки метрик request/user/booking id. Используйте тестовые данные и локальный профиль.

## Роли и входы

Роли: `player`, `admin`, `owner`. Роль хранится в Identity, сервисы получают её через `introspect`, а не из JWT, поэтому смена роли действует сразу.

| Кто      | Сайт и кабинет  | Админка `/admin/`                               | Раздел «Жалобы» |
| -------- | --------------- | ----------------------------------------------- | --------------- |
| гость    | каталог, вход   | перенаправляется на форму входа админки         | нет             |
| `player` | да              | сразу уходит на сайт, интерфейс не показывается | нет             |
| `admin`  | да (вход общий) | да                                              | нет (`403`)     |
| `owner`  | да (вход общий) | да                                              | да              |

**Почему вход общий.** Сайт и админка работают на одном origin (`localhost:8088`), поэтому cookie `shift_access` и `shift_refresh` у них одни. Вошёл на сайте владельцем — открыл `/admin/` и уже внутри. Разделение сделано по роли: фронтенд админки не рисует оболочку, пока не проверена роль, а настоящую защиту обеспечивает сервер, который проверяет роль на каждом запросе.

**Что не сделано.** Раздельные сеансы (отдельная cookie и вход для админки). Это потребовало бы изменений в Identity, прокси и обоих фронтендах. Если понадобится, стоит рассмотреть отдельный поддомен для админки.
