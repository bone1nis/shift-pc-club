# Тесты и проверки

В проекте несколько уровней проверок. Чем ниже уровень, тем он быстрее и точнее показывает, где сломалось; чем выше, тем ближе к тому, что видит пользователь.

| Уровень               | Что проверяет                                | Где лежит                      | Как запустить                                      |
| --------------------- | -------------------------------------------- | ------------------------------ | -------------------------------------------------- |
| Статические проверки  | стиль, ошибки в коде, типы                   | весь репозиторий               | `pnpm lint`, `pnpm format:check`, `pnpm typecheck` |
| Unit (Vitest)         | логика фронтенда без браузера и сервера      | `tests/unit`                   | `pnpm test:unit`                                   |
| Backend (PHPUnit)     | правила, права, база, брокер                 | `services/*/tests`             | `./scripts/backend.sh test`                        |
| E2E (Playwright)      | сценарии в настоящем браузере на живом стеке | `tests/e2e`                    | `pnpm test:e2e`                                    |
| Доступность (axe)     | WCAG 2.x A/AA на ключевых экранах            | `tests/e2e/axe*.spec.ts`       | входит в E2E                                       |
| Сбои и восстановление | убитый воркер, остановленный брокер          | `scripts/chaos-worker-kill.sh` | запуск вручную                                     |

Всё сразу (без E2E): `./scripts/check.sh all`. Только фронтенд: `./scripts/check.sh frontend`, только backend: `./scripts/check.sh backend`.

## Статические проверки

- **ESLint** (`pnpm lint`): ошибки и стиль в `apps`, `packages`, `tests`. Предупреждения недопустимы (`--max-warnings 0`). Здесь же правило `fsd/boundaries`, которое не даёт слоям FSD импортировать «вверх».
- **Prettier** (`pnpm format:check`, исправить — `pnpm format`): единое форматирование кода, JSON, CSS, Markdown.
- **TypeScript** (`pnpm typecheck`): проверка типов в UI-ките, админке и сайте.
- **Pint** и **PHPStan** (`./scripts/backend.sh lint`, `analyse`): стиль и статический анализ PHP во всех трёх сервисах.
- **Husky** перед каждым коммитом запускает `lint-staged`: форматирование и `eslint --fix` для добавленных в коммит файлов.

## Unit-тесты (Vitest)

Запуск: `pnpm test:unit`, с покрытием — `pnpm test:coverage`. Среда — jsdom, файлы `tests/unit/*.test.ts`.

| Файл                                  | Что проверяет                                                                          |
| ------------------------------------- | -------------------------------------------------------------------------------------- |
| `api-csrf`, `api-session-expiry`      | клиент API: CSRF-токен, повтор при `419`, обновление сессии при `401`, возврат на вход |
| `booking-selection`, `booking-submit` | выбор мест и интервала, двойной клик, устаревшие ответы, `409`, идемпотентный ключ     |
| `admin-club-time`                     | перевод времени клуба (Москва) в UTC и обратно, невозможные даты                       |
| `ui-date`, `ui-kit`                   | календарь и арифметика дат, поведение компонентов UI-кита                              |
| `schemas`                             | схемы Zod: формы входа (русские сообщения) и ответы API                                |
| `event-contracts`                     | JSON-схемы событий в `packages/contracts/events`                                       |
| `analytics`                           | события сайта (`page_view`, `booking_started`)                                         |

Для критичных модулей (`shared/api`, `create-booking`, `shared/format`) задан порог покрытия 80 % по строкам и функциям; для остального репозитория порога нет намеренно. Тесты проверяют результат для пользователя, а не устройство компонентов.

## Backend-тесты (PHPUnit)

Запуск: `./scripts/backend.sh test` (все сервисы) или `./scripts/backend.sh test booking`. На момент написания: Identity 18, Club 14, Booking 58 тестов.

**Тестовые базы изолированы.** Тесты идут только в базы `shift_<сервис>_test` под ролями `<сервис>_test`. Эти роли подготавливает `scripts/isolate-test-databases.py`: у роли нет прав на рабочие базы. Дополнительно `TestCase` каждого сервиса перед запуском проверяет, что подключение именно тестовое (окружение `testing`, нужная база и роль, нет `DB_URL`, роль не суперпользователь и не видит другие базы), иначе тест не стартует. Это защита от случайного сброса рабочих данных (такой инцидент однажды был). Тесты всегда идут в режиме `SHIFT_MODE=prod`, чтобы проверять строгие правила.

Что покрыто:

- **Booking:** цена и её фиксация, границы интервалов и пересечения, групповая атомарность, идемпотентность, конкурентные запросы на настоящем PostgreSQL, отмена, неявка, продление, пересадка, оплата, отчёты и CSV-выгрузка, ежедневные сводки, уведомления, события сайта, неприкосновенность тестовых баз (`DatabaseSafetyTest`).
- **RabbitMqIntegrationTest:** настоящий брокер: подтверждение публикации (confirms), дубли, повторы через очереди задержки, dead-letter. Каждый тест использует собственное пространство имён, поэтому работающие воркеры не затрагиваются.
- **Identity:** ротация refresh-токена и отзыв семейства, подпись CSRF и `Origin`, роли и блокировка, выход, восстановление пароля, русские сообщения валидации.
- **Club:** каталог, тарифы, профиль клуба, согласование обслуживания места с Booking.
- **OpenApiContractTest** (во всех сервисах): спецификация OpenAPI доступна и содержит ожидаемые пути. Типы фронтенда сверяются с ней командой `pnpm contracts:check`.

## E2E-тесты (Playwright)

Запуск: `pnpm test:e2e`. Тесты идут в двух проектах: `chromium` (Desktop Chrome) и `mobile` (Pixel 7). Один воркер, без параллельного запуска: тесты работают на общей базе.

**Нужен запущенный стек** (`./scripts/dev.sh` или `./scripts/start.sh`). Адрес по умолчанию `http://localhost:8088`, меняется переменной `E2E_BASE_URL`. Подмены API нет: тест регистрирует нового игрока, бронирует место, под администратором заселяет, смотрит сессию в кабинете и завершает. Тесты оставляют после себя только свои записи.

| Файл                                                  | Сценарий                                                                                 |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `booking-session`                                     | полный путь: регистрация → бронь → заселение → сессия в кабинете → завершение            |
| `registration`, `localization-and-prices`             | регистрация с клавиатуры, русские ошибки, расчёт цены «ставка × часы»                    |
| `landing`, `layout`                                   | лендинг (галерея, шаги, контакты, FAQ, JSON-LD), нет горизонтальной прокрутки, один `h1` |
| `axe`, `axe-private`                                  | axe на публичных экранах, кабинете игрока и всех разделах админки                        |
| `accessibility`                                       | клавиатура, фокус, подписи                                                               |
| `resilience`                                          | сбои сети, перенаправление на вход                                                       |
| `admin-session-actions`                               | продление и пересадка через диалоги                                                      |
| `admin-club-profile`, `admin-reports`, `admin-mobile` | профиль клуба, отчёты и CSV, админка на телефоне                                         |
| `grafana`                                             | дашборды видят данные (нужен профиль `monitoring`: `./scripts/start.sh --monitoring`)    |

Некоторые тесты пропускаются на одном из проектов намеренно (например, для десктопа достаточно одного прогона). Если упал тест, отчёт лежит в `playwright-report/` (`pnpm exec playwright show-report`), а трассировка в `test-results/`.

**Режим стенда.** В `SHIFT_MODE=dev` (по умолчанию) окно заселения открыто заранее, поэтому тест брони идёт около минуты. В `SHIFT_MODE=prod` тест ждёт настоящее окно заселения (до ~16 минут), для него запускайте `SHIFT_MODE=prod pnpm test:e2e` на стеке, поднятом в том же режиме. Лимиты входа в `dev` подняты, поэтому много прогонов подряд не упираются в `429`.

**Практические советы**

- Страница должна быть интерактивной до действий: используйте `waitForInteractive` из `tests/e2e/support/hydration.ts` (работает и на dev, и на prod-сборке).
- Перед проверками контраста дождитесь конца анимаций (`scan()` в `axe-private.spec.ts` это делает).
- Не запускайте `pnpm build` при работающем `nuxt dev`: он сломает dev-сервер.

## Сбои и восстановление

`scripts/chaos-worker-kill.sh` проверяет на живом стеке самую неприятную ситуацию: воркер Booking убит сигналом SIGKILL после того, как ему доставили сообщение, но до подтверждения. Сценарий: воркер замораживается, публикуется событие, воркер убивается, сообщение возвращается в очередь, воркер запускается заново и обрабатывает событие один раз, повтор того же `event_id` не создаёт дубль. Скрипт затрагивает только тестовое событие `club.catalog.updated` и одну строку `inbox`. Принцип описан в [Outbox и inbox](/developer/events).

Другие проверенные сценарии (остановка RabbitMQ без потери событий, остановка воркера, повторная отправка писем) перечислены в журнале разработчика; их покрывают интеграционные тесты и команды `events:publish`, `notifications:redispatch`.

## Визуальные снимки для документации

`tests/visual/docs-screens.mjs` делает скриншоты, которые лежат в `docs/public/screens` и показываются в руководствах. Запускать его нужно при заметном изменении интерфейса: `node tests/visual/docs-screens.mjs` при работающем стеке. Это не тест, а генерация материалов.

## CI

Файл `.github/workflows/quality.yml` на каждый коммит делает:

1. **Frontend:** установка зависимостей по lock-файлу, `./scripts/check.sh frontend` (форматирование, lint, типы, unit с покрытием, сборка), `pnpm audit --prod`.
2. **Backend:** сборка образа, запуск PostgreSQL, Redis, RabbitMQ и сервисов, изоляция тестовых баз, проверка актуальности типов API (`contracts --check`), `./scripts/check.sh backend` (Pint, PHPStan, PHPUnit).

E2E в CI не входят: они идут на локальном стеке (`pnpm test:e2e`) и перед сдачей запускаются вручную.

## Что запускать, когда

| Изменили                        | Запустите                                                                      |
| ------------------------------- | ------------------------------------------------------------------------------ |
| компонент UI-кита               | `pnpm test:unit`, история в Storybook, `pnpm typecheck`                        |
| страницу сайта или админки      | `pnpm lint`, `pnpm typecheck`, нужный E2E (`pnpm exec playwright test <имя>`)  |
| правило бронирования или сессий | `./scripts/backend.sh test booking`, E2E `booking-session`                     |
| API или контракт                | `./scripts/backend.sh test`, `pnpm contracts:generate`, `pnpm contracts:check` |
| события, воркеры, outbox        | `RabbitMqIntegrationTest`, `scripts/chaos-worker-kill.sh`                      |
| перед сдачей                    | `./scripts/check.sh all` и `pnpm test:e2e`                                     |
