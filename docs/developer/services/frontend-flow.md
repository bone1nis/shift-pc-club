# Как сервисы работают с фронтендом

Фронтенд (сайт и админка) не знает, сколько за ним сервисов: он видит один адрес и три группы путей. Эта страница показывает, что происходит за ним в типичных ситуациях. Общее устройство сервисов — в [обзоре](/developer/services/), устройство самого фронтенда — в [разделе про фронтенд](/developer/frontend).

## Кто за что отвечает для фронтенда

| Что нужно экрану                       | Откуда берётся   | Сервис   |
| -------------------------------------- | ---------------- | -------- |
| кто вошёл, роль, устройства            | `/api/auth/*`    | Identity |
| зоны, компьютеры, цены, контакты клуба | `/api/club/*`    | Club     |
| свободные места, брони, сессии, отчёты | `/api/booking/*` | Booking  |

Фронтенд никогда не обращается к `/internal/*`: прокси закрывает эти пути (`404`), они нужны только самим сервисам.

## Как сервис узнаёт, кто пришёл

Браузер отправляет cookie `shift_access` (JWT) на любой путь. Дальше каждый сервис делает одно и то же (`Authenticate`):

1. **Проверяет подпись токена** общим публичным ключом (RS256), издателя, аудиторию и срок. Секретный ключ есть только у Identity.
2. **Спрашивает Identity** (`POST /api/auth/internal/introspect` с секретом `INTERNAL_TOKEN`): сессия ещё действует, пользователь не заблокирован, какая у него роль сейчас. Это нужно, чтобы выход, блокировка и смена роли действовали сразу, а не после истечения 15-минутного токена.
3. Кладёт данные пользователя в запрос и передаёт контроллеру.

Если Identity недоступен, остальные сервисы отвечают `503 Identity verification unavailable`, а клиент API показывает ошибку «Сервис временно недоступен». Публичные пути (каталог, профиль клуба, доступность мест) от Identity не зависят.

## Типичные сценарии

### Открыть главную

```text
браузер → nginx → сайт (Nuxt, SSR)
   сайт (на сервере) → /api/club/catalog, /api/club/profile  (Club)
   сайт ← HTML с тарифами, залами, контактами
браузер ← готовая страница; дальше «оживает» (гидрация)
```

Идёт только чтение из Club. Доступность мест, Booking и Identity на главной не участвуют.

### Войти

```text
браузер → POST /api/auth/csrf         (Identity: выдаёт XSRF-TOKEN)
браузер → POST /api/auth/login        (Identity: проверяет пароль, создаёт сеанс)
браузер ← cookie shift_access (15 мин) и shift_refresh, данные пользователя
```

Дальше сайт хранит в Pinia только имя и роль. Пока токен действует, остальные сервисы работают как описано выше. Когда он истекает, клиент API сам вызывает `/api/auth/refresh` и повторяет запрос.

### Выбрать места и забронировать

```text
страница бронирования
  → GET /api/club/catalog                       (Club: схема зала, цены)
  → GET /api/booking/availability?start&end     (Booking: какие места свободны)
  → POST /api/booking/bookings                  (Booking)
        заголовок Idempotency-Key; в ОДНОЙ транзакции: проверка занятости,
        расчёт цены по копии тарифов, запись брони и мест, запись события в outbox
  ← 201 с бронью (или 409, если место уже занято)
```

Важная деталь: **при создании брони Booking не обращается в Club**. Он использует свою копию каталога (проекцию) и фиксирует цену на момент брони. Поэтому бронь работает, даже если Club временно недоступен ([ADR 0004](/adr/0004-booking-reservation-in-one-transaction)).

После ответа работает фон: `events:publish` отправляет событие `booking.confirmed` в RabbitMQ, `booking-worker` принимает его (inbox), создаёт уведомление и ставит письмо в очередь `notifications`; `booking-notification-worker` отправляет письмо. Пользователю письмо приходит на email, а запись появляется в разделе «Уведомления» кабинета (`GET /api/booking/notifications`); данные кабинета обновляются раз в 30 секунд.

### Заселить гостя (админка)

```text
кнопка «Заселить» → POST /api/booking/admin/bookings/12/check-in
  Booking: роль admin? бронь confirmed? сейчас внутри окна заселения?
  → создаёт игровую сессию(и), пишет аудит и событие booking.checked_in
  ← сессия; useOperationsStore.refresh() обновляет смену
```

В кабинете игрока сессия появится при ближайшем опросе (до 30 секунд).

### Вывести компьютер на обслуживание (админка)

Это единственное действие, которое затрагивает сразу два сервиса:

```text
админка → PATCH /api/club/admin/workstations/7   {status: maintenance}
   Club → POST /api/booking/internal/workstations/7/maintenance   (Booking блокирует место)
          Booking отвечает 409, если есть будущие брони или активная сессия
   Club сохраняет статус и пишет событие club.catalog.updated
   (если сохранить не вышло — Club просит Booking снять блокировку)
админка ← обновлённый каталог
```

Если Booking недоступен, Club отвечает `503`, и место остаётся рабочим: лучше отказать, чем получить расхождение. Подробности — в [ADR 0006](/adr/0006-maintenance-coordination).

### Изменить цену или профиль клуба

```text
админка → PATCH /api/club/admin/tariffs/3
   Club: сохраняет цену, поднимает версию, пишет аудит и club.catalog.updated (одна транзакция)
   Booking получает событие (и раз в минуту сверяется сам: club:sync) и обновляет копию каталога
```

Новая цена действует для **новых** броней; уже оформленные сохраняют прежнюю.

### Отчёт и CSV

Страница «Отчёты» запрашивает `/api/booking/admin/reports` (Booking считает по своей базе). CSV-выгрузка уходит в очередь `reports`, готовый файл скачивается отдельным запросом ([подробно](/developer/services/booking#csv-выгрузка-отчёта)).

## Что видит пользователь, когда что-то недоступно

| Недоступно     | Что происходит                                                                                                                                            |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity       | вход и проверка сессии не работают; остальные сервисы отвечают `503`; публичный каталог открывается                                                       |
| Club           | главная и страница бронирования не получают каталог (показывается ошибка с повтором); оформление брони по уже загруженной схеме и данные Booking работают |
| Booking        | схема мест, брони, кабинет и отчёты недоступны; вход и главная работают                                                                                   |
| RabbitMQ       | бронь и сессии создаются как обычно; события копятся в `outbox` и уходят после восстановления (письма и сверка каталога задерживаются)                    |
| воркер Booking | письма и обработка событий ждут в очереди и выполняются после запуска ([проверка](/developer/testing#сбои-и-восстановление))                              |

Во всех случаях клиент API превращает ошибку в понятное сообщение и кнопку «Повторить», а не пустой экран.
