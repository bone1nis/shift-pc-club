# Отдельная база PostgreSQL для каждого сервиса

**Статус:** принято, 13 октября 2026.

## Контекст

Identity, Club и Booking развиваются независимо и не должны читать таблицы друг друга.

## Решение

У каждого сервиса своя база и роль. Данные других сервисов Booking хранит как проекцию (каталог из snapshot API Club), а пользователей проверяет через внутренний API Identity. Метрики и дашборды читают отдельные read-only представления `reporting_*` под ролью `shift_report`. Тесты используют выделенные базы `shift_*_test` с отдельными ролями.

## Последствия

Нет межсервисных join-ов и общих транзакций; согласованность обеспечивают события и явные внутренние вызовы (например, перевод места на обслуживание).

## Альтернативы

Одна общая база — проще, но размывает границы и мешает независимым миграциям.
